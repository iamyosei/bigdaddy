# 代理回答の型集（既定）

前段で利用者に聞きたくなったとき、ここに当てはまれば聞かずに代理で決め、指示書の「代理で決めたこと」に書く。
利用者の手元に `~/.claude/bigdaddy/proxy-answers.md` があれば、先にそれを読む。同じ状況の行は手元のファイルを優先する。この表は、無いときの既定。
利用者が代理の判断を覆したら、手元のファイルを直す。

| 状況 | 既定の答え方 |
|---|---|
| 推奨付きの選択肢を出した | 推奨を採る |
| 効果を主張する | 数字を付ける（時間・トークン・件数・容量）。数字の無い「速くなった」は通さない |
| 同じ箇所への修正が重なってきた | 一度止まり、全体の設計を見直す。足す前に統合・削除を考える |
| 本番データを触る | DB に直接つながない。管理画面の API や job を使う |
| 一括処理・バックフィル | 効果の大きい対象から小さく試し、リスクを確かめてから広げる |
| 完了の確かめ方 | 実機・実データで。ログイン状態・端末など条件を書く |
| UI の見た目 | 色・余白・文言などの値は、DESIGN.md とデザイントークンに揃え、周りの画面のトンマナに合わせる（代理で決めてよい）。画面の構成・操作・状態（部品の追加や差し替え、空・エラーなどの状態を含む）が変わる依頼は、代理で決めず、画面設計を作って利用者に見せる（`briefing` の「画面設計」節）。実装中は見た目を聞かない |
| 状態設計の読み手（`statechart` の reader）が決まらない | 利用者 |
| 状態遷移が変わるか迷う | 変わるとみて状態設計を作る（`briefing` の「状態設計」節） |
| 新しい feature flag | 付けない。付けるなら指示書を作る段階で本人に聞き、「仕様で決めたこと」に書く |
| 外部への送信 | 指示書を作る段階で本人に聞き、「仕様で決めたこと」に書く。実装セッションには聞かせない |
| 実装中の設計の変更（取り消せるもの） | 局所的なもの（関数名、内部の型の切り方など）は、実装セッションが自分で決め、「判断の記録」に残す。手段の変更、他の指示書への影響、画面設計・状態設計との差は、親に返して親が決める（`briefing` の「親に返すもの」）。利用者は、topic から default branch への PR で後から見る |
| 設計や全体の方針の決定 | 子に渡す前に親が決め切る。「あとは淡々と実装をやるだけ」の状態になってから子を立ち上げる |
| 外部ツールが「使えない」と見えた | `ToolSearch` で探す。認証切れなら本人に再認証を頼む |
