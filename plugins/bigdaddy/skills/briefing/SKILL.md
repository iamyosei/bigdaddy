# briefing

目的はひとつ。pstack の poteto-mode に、本質的で十分に詳細な指示書を渡すこと。
依頼の形は問わない。「ここをこうして」でも「この画面、こうだからあーしたい」でも「なんか遅い」でも、同じ手順で指示書の空欄を埋める。
実装はしない。前段の会話を実装セッションに持ち込まないことで、実装側の文脈をきれいに保つ。

優先順位: 利用者の指示・project の CLAUDE.md > project の skill > このファイル > pstack。

## 十分さの基準

`references/brief-template.md` の項目が全部埋まれば十分。依頼にすでに書いてある項目は、そのまま使う。

| 項目 | 埋まったと言える状態 |
|---|---|
| プレイブック | poteto-mode のプレイブックのどれかに決まっている。`bigdaddy:jev-gates` の `scripts/route-playbook.sh` で判定する。`confidence` が 0.5 未満なら top3 から自分で選び、`none` なら poteto-mode に渡さず利用者に返す。Jev が無効（exit 3）のときは、`route-playbook.sh --criteria` の一覧から自分で選ぶ |
| 推奨モデル | `bigdaddy:jev-gates` の `scripts/route-model.sh --session <playbook>` が返すモデルと effort になっている（Jev は呼ばない）。Feature・Refactoring は sonnet high、それ以外は opus medium。指示書の冒頭に書く |
| 使う原則 | 原則 skill が 2〜4 個、`principle-<name>` の名前と、この作業でどう効くかの 1 行で書けている。選ぶ元は、選んだプレイブックの本文が名指しする原則と、poteto-mode の Principles 節で「いつ使うか」が作業に当たる原則。Bug fix なら `principle-fix-root-causes` を必ず入れる。4 個を超えたら、この作業での効き方が具体的に書けないものから落とす。この項目は「未定」にしない |
| 対象 | ファイル・関数・ルートのパスまで特定できている |
| 今 → 望む状態 | 完了後に観察で確かめられる形で書けている |
| なぜ | 依頼の背景が書けている。指示どおりの単純な変更なら「指示どおり」でよい |
| データの形 | 扱う値と持ち主が書けている。無関係なら n/a と理由 |
| 成功条件と確かめ方 | どこで・どの条件で・何が見えたら完了かが書けている。Bug fix で安く局所的な回帰テストが書けるなら、pstack の `tdd`（SKILL.md を Read ツールで読む）で先に失敗するテストを書くと書いてある。成功条件が画面・CLI・サービスの振る舞いで、作業リポジトリにそれを操作して確かめるスクリプトも project の verification skill も無ければ、実装役が pstack の `create-verification-skill`（SKILL.md を Read ツールで読む）で project-local の verification skill を作って確かめると書いてある |
| 受入条件・不変条件 | 不変条件が「〜は全部。除外は X だけ」の閉じた全称で書けている。比べる・守る項目を列挙したなら、列挙が不変条件の全量と一致することを点検してある（食い違えば不変条件の側を正本にして列挙を直す）。隔離レビュアーにこの節の原文を渡し、`bigdaddy:review-triage-loop` の `references/isolated-review.md` の「レビュアーへの指示」のとおり（利用者に見える値から逆にたどる）不変条件を確かめさせると書いてある |
| 設計 | 子が始まる時点で、実装役が設計の選択をせずに進められる状態。指示書の「データの形」「設計」「画面設計」「状態設計」の 4 節に、データの形、型とシグネチャ、モジュールやファイルの境界、変えるファイルと関数、要になる手順、（画面が変わる依頼なら）画面設計の URL、（状態遷移が変わる依頼なら）合意した状態設計が決まっている。指示書の外に出る設計の選択は全部、親が決める（除外は、親が応答できず利用者に返したものだけ）。重い設計は親が pstack の `architect`（SKILL.md を Read ツールで読む）で詰める。親はコードを書かず、型やシグネチャは指示書に書くだけ。この項目は、opus medium に渡すものを除いて「未定」にしない。原因が未確定の Bug fix・Perf issue など opus medium に渡すものは、原因の調査と設計が指示書の内で子の担当なので、「設計」は「調査のあとに子が決める」でよく、この行の対象外。ただしその子も、「親に返すもの」の（a）〜（c）は親に返す |
| 画面設計 | 画面が変わる依頼は、利用者が合意した画面設計の URL が 1 つある（「画面設計」節）。除外は、その節の基準に当たる変更だけ。除外のときは n/a と理由 |
| 状態設計 | 状態遷移が変わる依頼は、利用者が合意した状態設計の Mermaid ソースとルールの一覧がある（「状態設計」節）。除外のときは n/a と理由 |
| 範囲外 | ついでにやりそうなことが除外されている |
| 仕様で決めたこと | この作業が外部への送信（Slack・顧客・外部サービス）と新しい feature flag の追加を含むかが決まっている。含むものは、宛先・内容・名前・既定値まで書く。含まなければ「なし」。決められないものは、渡す前に利用者に聞く |

## 本質さの基準

十分でも、依頼された変更が本当の必要とずれていれば意味がない。次の危険信号があるときだけ、`references/naze-naze.md` のなぜなぜ分析で根本原因まで掘る。

- 依頼された変更と、それで解決したい問題が別の層にある（画面が遅い → 画面を直したい、だが原因は API やデータ）
- 同じ場所への修正が git の履歴に繰り返し出ている
- 「一旦」「とりあえず」が付いている
- 最近のマージの直後に出た問題
- 「遅い」「多い」に数字が無い

危険信号が無ければ、依頼どおりに受け取ってよい。迷ったら `bigdaddy:jev-gates` で「依頼された変更は根本原因と違う所に効いているか」を聞き、高ければ掘る。Jev が無効（exit 3）なら自分で同じ問いに答える。それでも迷えば掘る側に倒す。
利用者が「原因はわかってる」「そのままやって」と言ったら掘らない。

## 埋め方

空欄は次の順で埋める。前の手段で埋まるなら次に進まない。

1. **観察する。** コード・画面・ログ・データ・git 履歴を見る。観察で答えが出る問いは人に聞かない。仕組みを読むなら pstack の `how`、経緯なら `why`（SKILL.md を Read ツールで読む）。
2. **代理で答える。** 利用者の手元の `~/.claude/bigdaddy/proxy-answers.md` があれば先に読み、無ければ `references/proxy-answers.md` を読む。同じ状況の行が両方にあるときは手元のファイルを優先する。当てはまる行があれば、聞かずに決めて指示書の「代理で決めたこと」に書く。
3. **聞く。** 好み・仕様など、観察でも代理でも埋まらないものだけ。1 回に 1〜3 問、推奨を付けて `AskUserQuestion` で聞く。`AskUserQuestion` が使えない環境では、同じ形で本文に書いて止まる。外部送信と新しい feature flag はここで聞いて「仕様で決めたこと」に書く。実装セッションに聞かせない。

単純な依頼なら、観察だけで全部埋まり、質問ゼロで渡せるのが普通。
画面が変わる依頼の見た目と操作は、文章で聞かず、画面設計で見せて決める（次の節）。状態遷移は、状態設計の図とルールで見せて決める（「状態設計」節）。

## 画面設計

画面が変わる依頼では、指示書を渡す前に、決めた仕様を反映した画面設計を作り、利用者に見せて合意を取る。画面の食い違いを最後の QA まで持ち越さず、実装中の見た目の質問と手戻りを減らすため。画面設計は仕様の一部で、実装ではない。このセッションが作ってよい。

- **対象。** 新しい画面と、既存画面の構成・操作・状態が変わる依頼は全部。除くのは、要素の数・配置・操作の流れ・状態が変わらず、文言・色・余白などの値の差し替えだけで済む変更。除いたときは、指示書の「画面設計」に n/a と理由を書く。
- **道具。** 作業リポジトリの CLAUDE.md・AGENTS.md・DESIGN.md や project の skill が、画面設計の道具や手順（Figma のファイルなど）を指定していれば、それを最優先で使う。指定が無ければ Claude Design（`Artifact` の Design 型。作り方は `action: "quickstart"`、`intent: "design"`）を使う。指定の道具が使えない（認証切れなど）ときは、黙って飛ばさず、利用者に再認証を頼むか、Claude Design で代える。
- **デザインシステム。** 作業リポジトリの DESIGN.md・デザイントークンがあればそれに揃える。無ければ、組織の既定のデザインシステムを使う。
- **作り方。** 「今 → 望む状態」と「仕様で決めたこと」を反映する。成功条件に出てくる状態（空・エラー・読み込み中など）も 1 つずつ描く。画面に出す文言も画面設計に書き、実装役はそれを正本にする。決めた仕様に無い要素は足さない。
- **見せる。** URL を利用者に見せて、レビューしてもらう。指摘が出たら画面設計を直して、同じ URL で見せ直す（URL は変えない。合意の記録に、合意した日付を書く）。利用者の合意の返答を得るまで、指示書は渡さない。「お願い」「いいよ」も合意として扱う。
- **記録。** 合意は、利用者の返答の要約と日付を、指示書の「仕様で決めたこと」に書く（「代理で決めたこと」には書かない）。URL は、指示書の「画面設計」節に 1 つ書く。
- **topic の流れ。** 指示書が 2 枚以上のときは、全部の指示書を渡す前に、全部の画面を 1 つの画面設計にまとめて、レビューを 1 回で済ませる。URL は、各指示書の「画面設計」と、最終 PR の状態の JSON の `design` に書く。
- **あとから足す指示書。** QA の blocking や利用者の指示で足す指示書が、画面の構成・操作・状態を変えるときは、同じ URL の画面設計を直して利用者に見せ直し、合意を取ってから渡す（記録の日付を更新する）。再 QA は、直した画面設計に当たる全部の画面を照合し直す。画面の構成・操作・状態が変わらない修正は、いまの画面設計のままでよい。
- **実装中は画面設計を変えない。** 実装中は、合意済みの画面設計を変えない。画面の構成・操作・状態を変える差は、「親に返すもの」の（b）でも（c）でも、実行中の行には入れない。親が決めて、子 PR の「判断の記録」に親の決定として書き、最終 PR の確認で利用者が見る。直す必要があれば、利用者の指示として足す指示書（「あとから足す指示書」）で画面設計を直し、合意を取り直す。未着手の行は、渡す前なので、画面設計を直して合意を取り直してから渡してよい。構成・操作・状態が変わらない細部は、親が決めて終わりにする。
- **実装中。** 見た目・文言・操作は、画面設計を正本にする。画面設計が決めていない細部は、DESIGN.md・デザイントークン・周りの画面に揃える。見た目について利用者には聞かない。画面設計どおりに作れないときは、実装役が決めず、「親に返すもの」の（c）として親に返す（親の扱いは上の「実装中は画面設計を変えない」）。親が決めた差は、親の決定として PR 本文の「判断の記録」に書く。画面設計との差は、「本人に必ず返すもの」の方針の転換に当たらない。
- **QA。** QA は、画面設計と実装の画面を並べて照合する（`references/brief-template.md` の「QA subagent への依頼の型」）。QA には判断の記録を渡さないので、QA が画面の blocking にした差のうち、構成・操作・状態を変えない差で、親が承認して子 PR の「判断の記録」に親の決定として書いてあるものだけ、親が advisory に下げて最終 PR に載せる。画面設計の照合で確かめられなかった画面は、最終 PR の「人間が確かめること」に載せる。
- **画面設計を作れないとき。** Artifact も指定の道具も使えない環境では、黙って飛ばさず、画面設計を作れないことと理由を利用者に伝え、利用者が、画面設計を作れる環境の briefing で作ってから進める（除外には使わない）。

## 状態設計

状態遷移が変わる依頼では、指示書を渡す前に、状態の図とルールを作って検査し、利用者に見せて合意を取る。画面設計や会話で決めた、曖昧だが重要な仕様を、検査できる決定論的な形にするため。ルールを破る経路は実装の前に設計のバグとして見つけ、実装の後はコードが状態設計どおりかを照合する。画面設計と同じく仕様の一部で、このセッションが作ってよい。

- **対象。** システムの状態か、状態の間の移り方を足す・変える・消す依頼は全部（画面をまたぐ操作の流れ、リトライ・タイムアウト・キャンセル、並行処理や競合、外部とのプロトコル、ジョブや購読などのライフサイクル）。除くのは、状態も移り方も変わらない変更。除いたときは、指示書の「状態設計」に n/a と理由を書く。迷ったら作る。
- **道具。** pstack の `statechart`（SKILL.md を Read ツールで読む。Skill ツールでは起動できない）の Chart to spec の手順 1・2（`render` と `from-chart`）。向きは Chart to spec に固定する。読み手（reader）は利用者で、ラベルは利用者が見る・気にする言葉にする。作業ファイルと PNG はリポジトリの外（scratchpad）に置く。初回は TLC と Java を mise で約 305MB 入れる。
- **作り方。** 「今 → 望む状態」「仕様で決めたこと」、画面設計の状態と操作、利用者との会話で決めたことから図を作り、ルールは利用者の文で 1 本ずつ `%% never` 行に書く。状態の組で書けないルール（回数など）は、それを表す状態を図に足して書き、落とさない。`from-chart` で壊れたルールは設計のバグなので、図かルールを直すか、利用者に見せる項目に入れる。ルールを弱めて通さない。
- **見せる。** PNG、ルールの一覧、`from-chart` で見つけて直した設計のバグを、「合意と受け渡し」の 1 回の確認にまとめる。合意の返答を得るまで指示書は渡さない。
- **記録。** 合意は、利用者の返答の要約と日付を「仕様で決めたこと」に書く。Mermaid ソースは指示書の「状態設計」節に貼る。ルールは「受入条件・不変条件」の不変条件に、利用者の文のまま写す（`never` は到達する全部の状態についての文なので、「〜は全部。除外は X だけ」の形に書き直さない）。
- **実装中。** 状態と移り方は状態設計を正本にする。状態設計どおりに作れないときは、実装役が決めず、「親に返すもの」の（c）として親に返す。親の扱いは、画面設計の「実装中は画面設計を変えない」を状態設計に読み替えたものと同じ。状態設計との差は、「本人に必ず返すもの」の方針の転換に当たらない。
- **実装後の照合。** 実装役は、指示書の Mermaid ソースを `from-chart` に通した spec を合意した spec とし、コードを写したモデルを `from-spec <コードのモデル> --against <合意した spec>` で照合する。差がコードの誤りなら直し、状態設計どおりに作れない差は（c）で親に返す。隔離レビュアーは、モデルの条件が実コードの file:line と合うかを確かめる。手順は指示書の型の「状態設計」節。
- **作れないとき。** mise・ネットワーク・Java が使えないなどで作れないときは、黙って飛ばさず、利用者に理由を伝えて、状態設計なしで進めるかを聞く。

## 分ける

指示書は 1 枚 = 1 セッション = 1 PR。

- 原因や変更が独立して複数あれば、指示書を分ける。分けるか束ねるかは `bigdaddy:jev-gates` で決める（Jev が無効なら、依存と触るファイルを見て自分で決める）。
- なぜなぜ分析をしたときは、応急処置と恒久対策を別の指示書にする。依頼された変更を断るのではなく、両方並べる。
- 依存の順序を付ける。各指示書に、前提の指示書を書く。同じファイルを触る指示書どうしも依存として扱い、直列にする。依存の無いものは最初から並行に回す。
- project の CLAUDE.md がバックログ（Notion など）への登録を求める場合は、指示書ごとにバックログの行を作る。PR に貼る URL がここで決まる。バックログのツールが見えなければ `ToolSearch` で探す。認証切れなら黙って飛ばさず、利用者に再認証を頼む。

### 1 枚か、2 枚以上か

- 1 枚: default branch（例: main）向けの PR 1 本。マージは利用者がする。
- 2 枚以上: topic branch に子 PR を集め、最後に topic から default branch への PR 1 本（最終 PR）を利用者が確かめてマージする。親は、指示書ごとの状態を、最終 PR（draft）の本文の JSON に持つ。手順は `references/topic.md` を Read ツールで読んで従う。

## 決めたら点検する

プレイブックの選択、掘るか掘らないか、分けるか束ねるか、見立ては、決めたら `bigdaddy:logic-audit` の決定モードで点検する。指示書の「設計」が、「なぜ」に本質的に沿っているか（やろうとしていることが目的に合っているか）も、hook の求めとは別に、子に渡す前に必ずここで点検し、結果を「代理で決めたこと」か「仕様で決めたこと」に書く。重要と判定されたものは、指示書の「代理で決めたこと」に結論・前提・退けた代案・覆る条件を書く。jev-gates のスクリプトを実行すると hook が点検を求めるので、そのときに行う。

## 合意と受け渡し

次のどれかに当たるときは、渡す前に利用者に見せて合意を取る。

- 見立てが依頼と違う（依頼された変更とは別の手当てを提案する）
- 代理で決めたことに、外れると手戻りが大きいものがある
- 画面が変わる依頼（除外は「画面設計」節の基準に当たる変更だけ）で、画面設計に利用者の合意が無い。見せる形は画面設計の URL で、他の項目と同じ 1 回の確認にまとめる
- 状態遷移が変わる依頼（除外は「状態設計」節の基準に当たる変更だけ）で、状態設計に利用者の合意が無い。見せる形は PNG とルールの一覧で、他の項目と同じ 1 回の確認にまとめる

見せる形:

```text
依頼: <利用者が言ったこと>
見立て: <本当の必要・根本原因>（根拠: <証拠>）
提案: <指示書の要約>（応急処置 / 恒久対策）
画面設計: <URL>（画面が変わる依頼のときだけ。見てほしい点を添える）
状態設計: <PNG のパス>（ルール N 本）（状態遷移が変わる依頼のときだけ。ルールの一覧と、直した設計のバグを添える）
```

見立てが依頼と違うときは、見せる前に `bigdaddy:logic-audit` の決定モードで見立てを点検する。根拠が支える強さで書き（「〜だ」と「〜の可能性が高い」を区別する）、未確認の前提は前提として示す。

どれにも当たらなければ合意を省いて渡す。
渡すときは `references/brief-template.md` の指示書を `spawn_task`（このアプリでは `start_session`）のプロンプトにする。どちらも使えない環境（Cursor など）では、指示書を返信の本文に出し、利用者が新しいチャットに貼れるようにする。
指示書を書くこのセッションは計画役なので opus medium で動かす。実装セッションの主は、指示書の推奨モデル（`route-model.sh --session <playbook>`）で動かす。Feature・Refactoring は設計が指示書で決まっているので sonnet high、原因が未確定の Bug fix・Perf issue などは opus medium。

0. 指示書が 2 枚以上のときは、先に topic を切って push し、draft の最終 PR を作り、各子の `start_session` で新しい worktree の元のブランチに topic を指定する（`source_branch`）。指定できない環境では、子の指示書の「repo の約束」に、topic を元に worktree を作ると書く。
1. `start_session` を `context: "fresh"` で呼ぶときは、`model` に推奨モデルの id、`effort` に推奨の effort を渡す。id は family 名ではなく、モデルの選択メニューの id（例: sonnet なら `claude-sonnet-5-5`）。この引数は親と同じか安いモデルだけ受け付け、高いモデルは無視される。
2. 引数で渡せなかったとき（`offer` カードや提案カードから利用者が始めた場合など）は、開いたあとに切り替える。この経路でも、カードの `title` には、`<ID>: <要約>` を付ける。開いたあとの子は、親が `references/topic.md` の手順 3 の照合で見つけ、JSON の `session` に id を書く。カードの task_id は、カードを出して返ったらすぐ `card` に書く。`list_sessions` を `linked: true` で呼んで子セッションの `sessionId` を取り、`model` が推奨と違えば `set_session_model` に推奨モデルの id を、`set_session_effort` に推奨の effort を渡す。切り替わるのは次のターンからなので、最初のターンは開いたときのモデルで動く。セッションは自分のモデルを変えられない（`set_session_model` は自分自身を対象にすると断られる）。
3. 子セッションが見つからない、または切り替えが断られたときは、利用者に「実装セッションのモデルを <id>、effort を <effort> に、モデルの選択メニューで変えてほしい」と伝える。`spawn_task` が無い環境（クラウドセッション、CLI など）では、指示書を本文に出す。利用者が同じセッションでの実装を認めたら pstack の `poteto-mode` と指示書の「使う原則」の SKILL.md を Read ツールで読んで切り替え、認めなければ新しいセッションに貼れる形で渡して止まる。依存のあるものは、前の指示書の子 PR が topic にマージされてから渡す。指示書が 1 枚なら、渡したあとは、子の PR が出るまで、子からの `SendMessage`（「親に返すもの」）に応じる。2 枚以上なら、全部の子が topic に入り、親が QA を回して最終 PR を ready にするまで、親は待つ。

## 本人に必ず返すもの

実装セッションが利用者に返す項目はここだけ。親に返す項目は、次の「親に返すもの」にある。指示書の「本人に返すもの」と「親に返すもの」には、それぞれの節をそのまま貼る。ここに無いものは、実装中に利用者に聞かない。前段（briefing）が渡す前に聞くものは、「埋め方」と「合意と受け渡し」に書いてある。

返す:

- default branch（例: main）への PR のマージ。agent は default branch に入れない。topic branch への子 PR は、隔離レビュー済みの head なら子セッションがマージする。
- 本番データへの書き込み
- 指示書の「仕様で決めたこと」に書かれていない外部への送信（Slack、顧客、外部サービス）と、新しい feature flag の追加。書かれた範囲なら聞かずに実行する。
- 方針の転換。指示書の「今 → 望む状態」または「成功条件」を書き換えないと完了できないときだけ。

返さない:

- 上に当たらず、「親に返すもの」にも当たらない局所的な設計の選択（関数名、内部の型の切り方など）。自分で決め、PR 本文の「判断の記録」に結論・前提・退けた代案・覆る条件を残す。topic の場合、記録は最終 PR に集まり、利用者が後から見る。

上の 4 項目のどれに当たるか迷うときは、あとから取り消せるかで分ける。取り消せるなら、次の「親に返すもの」に当たらない限り、決めて記録する。取り消せないなら、設計の選択は親に、それ以外は利用者に返す。

## 親に返すもの

設計や全体の方針を決める意思決定は、親（briefing のセッション）が渡す前に済ませる。子に渡す時点で、指示書の「設計」は「あとは淡々と実装をやるだけ」の状態になっている（「十分さの基準」の「設計」。opus medium に渡すものを除く）。指示書に無い設計の選択が出たときは、次の（a）〜（c）のどれかに当たるものを、実装役が決めずに親に返す。（d）は設計の選択ではないが、同じ経路で親に返す。

- （a）「今 → 望む状態」に至る手段を変えるもの
- （b）他の指示書や全体の方針に影響するもの
- （c）画面設計・状態設計との差
- （d）2 回目以降の隔離レビューで出た blocking。設計の選択ではないが、実装役は直さず、指摘の全文を親に送る（下の「blocking の仕分け」）

当たらない局所的な設計の選択は、「本人に必ず返すもの」の「返さない」のとおり、実装役が決めて記録する。1 回目の隔離レビューの指摘のうち設計の変更が要るものも、（a）〜（c）に当たれば親に返す。

返し方:

- 親には `SendMessage` で送る（deferred tool なので、先に `ToolSearch` で `select:SendMessage` を読み込む）。`to` は、指示書の「親に返すもの」に書かれた親セッションの id（`local_…`）。親は自分の id を `mcp__ccd_session_mgmt__get_session` の `session_id: "self"` の `sessionId` で得て、指示書に書く。子は、指示書の id に加えて、自分の `get_session("self")` の `parentSessionId` からも親を求められる。どちらも得られない環境（Cursor など）では、親に返す経路が無いので、利用者に返す。
- 送るときは、その部分の作業を止め、影響しない部分は進める。送る文面は、何を決めたいか、候補と推奨、止めた部分と進めた部分を、最初の 1 行で分かるように書く。
- 親は、受け取ったら、決めて（重要なものは「決めたら点検する」のとおり点検して）、同じ送信元に `SendMessage` で返す。他の指示書に影響する決定は、親が該当する指示書も直す。未着手の行は、指示書本文と、topic なら最終 PR 本文の `<details>` の全文を直し、実行中の行は `SendMessage` で伝える。決定が画面の構成・操作・状態を変えるときの扱いは、「画面設計」節の「実装中は画面設計を変えない」に従う（実行中の子には、現行の画面設計のまま進めるよう伝える。状態設計を変えるときも同じ）。親は、子の「判断の記録」の親の決定を、自分が送った決定と照合してから、QA の blocking を advisory に下げる。照合できないとき（親を閉じて再開したなど）は、下げずに全体の `qa` を「要確認」にする。再開した親は、実行中の子に、新しい親の id を `SendMessage` で伝える。子は、親の決定を PR 本文の「判断の記録」に「親の決定」として書く。
- 親が応答できないとき（`get_session` で親が `isArchived` になっている、または、影響しない部分を終えても返信が来ない）は、止めた部分を未決として PR 本文に書き、利用者に返す。topic の子は、止めた部分が残るあいだは topic にマージせず、完了を報告して止まる（親は `bigdaddy:briefing` の `references/topic.md` の手順 4 の「止まった子」として扱い、行を「要確認」にする）。これが、設計と見た目の選択が利用者に届く唯一の経路になる。

### blocking の仕分け

隔離レビューの回ごとの範囲は `bigdaddy:review-triage-loop` の `references/isolated-review.md` の「回ごとの範囲」に、2 回目以降の blocking を親に送ってから親が仕分けて記録するまでの流れは、同じ skill の SKILL.md の「2 回目以降の blocking」に従う。親も子も同じ節を読む。

## 返し方

- 日本語で短く。結論が先。
- 選択肢には推奨を 1 つ付ける。
- 効果や規模は数字で示す。

## 文章

日本語の文章は yomiyasu（`yomiyasu:yomiyasu`）の基準で書く。書く物の重さで使い方を変える。

| 書く物 | 使い方 |
|---|---|
| 会話の返答 | yomiyasu の本文は読まず、`references/writing.md` の要点だけ守る。本文は約 66KB あり、毎ターン読むと会話が太る |
| ドキュメント、PR の概要、Issue、コミット本文、Notion のページ | pstack の `technical-writing` と `unslop`（SKILL.md を Read ツールで読む。Skill ツールでは起動できない）で下書きを書き（構成と文の規律）、最後に yomiyasu で日本語として推敲してから出す。長い文書や会話が長いときは、推敲を subagent に渡し、仕上がった本文だけを受け取る |
| 英語の文章 | pstack の `technical-writing` と `unslop`（SKILL.md を Read ツールで読む） |

順番は `technical-writing` → `unslop` → yomiyasu に固定する。食い違ったときは、日本語の表現については yomiyasu を優先する。yomiyasu は今までどおり Skill ツールで起動する。yomiyasu と他の日本語推敲の skill（`japanese-tech-writing` など）は重ねない。
