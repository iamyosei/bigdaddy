# briefing

目的はひとつ。pstack の poteto-mode に、本質的で十分に詳細な指示書を渡すこと。
依頼の形は問わない。「ここをこうして」でも「この画面、こうだからあーしたい」でも「なんか遅い」でも、同じ手順で指示書の空欄を埋める。
実装はしない。前段の会話を実装セッションに持ち込まないことで、実装側の文脈をきれいに保つ。

優先順位: 利用者の指示・project の CLAUDE.md > project の skill > このファイル > pstack。

## 十分さの基準

`references/brief-template.md` の項目が全部埋まれば十分。依頼にすでに書いてある項目は、そのまま使う。

| 項目 | 埋まったと言える状態 |
|---|---|
| プレイブック | poteto-mode のプレイブックのどれかに決まっている。`bigdaddy:jev-gates` の `scripts/route-playbook.sh` で判定する。`confidence` が 0.5 未満なら top3 から自分で選び、`none` なら poteto-mode に渡さず利用者に返す。Jev が無効（exit 3）のときは、`route-playbook.sh --criteria` の一覧から自分で選ぶ |
| 推奨モデル | `bigdaddy:jev-gates` の `scripts/route-model.sh --session <playbook>` が返すモデルと effort になっている（Jev は呼ばない）。Feature・Refactoring は sonnet high、それ以外は opus medium。指示書の冒頭に書く |
| 使う原則 | 原則 skill が 2〜4 個、`principle-<name>` の名前と、この作業でどう効くかの 1 行で書けている。選ぶ元は、選んだプレイブックの本文が名指しする原則と、poteto-mode の Principles 節で「いつ使うか」が作業に当たる原則。Bug fix なら `principle-fix-root-causes` を必ず入れる。4 個を超えたら、この作業での効き方が具体的に書けないものから落とす。この項目は「未定」にしない |
| 対象 | ファイル・関数・ルートのパスまで特定できている |
| 今 → 望む状態 | 完了後に観察で確かめられる形で書けている |
| なぜ | 依頼の背景が書けている。指示どおりの単純な変更なら「指示どおり」でよい |
| データの形 | 扱う値と持ち主が書けている。無関係なら n/a と理由 |
| 成功条件と確かめ方 | どこで・どの条件で・何が見えたら完了かが書けている |
| 受入条件・不変条件 | 不変条件が「〜は全部。除外は X だけ」の閉じた全称で書けている。比べる・守る項目を列挙したなら、列挙が不変条件の全量と一致することを点検してある（食い違えば不変条件の側を正本にして列挙を直す）。隔離レビュアーにこの節の原文を渡し、利用者に見える値（画面・通知・課金額）から逆にたどって不変条件を確かめさせると書いてある |
| 設計 | 子が始まる時点で、実装役が設計の選択をせずに進められる状態。指示書の「データの形」「設計」「画面設計」の 3 節に、データの形、型とシグネチャ、モジュールやファイルの境界、変えるファイルと関数、要になる手順、（画面が変わる依頼なら）画面設計の URL が決まっている。指示書の外に出る設計の選択は全部、親が決める（除外は、親が応答できず利用者に返したものだけ）。重い設計は親が pstack の `architect`（SKILL.md を Read ツールで読む）で詰める。親はコードを書かず、型やシグネチャは指示書に書くだけ。この項目は、opus medium に渡すものを除いて「未定」にしない。原因が未確定の Bug fix・Perf issue など opus medium に渡すものは、原因の調査と設計が指示書の内で子の担当なので、「設計」は「調査のあとに子が決める」でよく、この行の対象外。ただしその子も、「親に返すもの」の（a）〜（c）は親に返す |
| 画面設計 | 画面が変わる依頼は、利用者が合意した画面設計の URL が 1 つある（「画面設計」節）。除外は、その節の基準に当たる変更だけ。除外のときは n/a と理由 |
| 範囲外 | ついでにやりそうなことが除外されている |
| 仕様で決めたこと | この作業が外部への送信（Slack・顧客・外部サービス）と新しい feature flag の追加を含むかが決まっている。含むものは、宛先・内容・名前・既定値まで書く。含まなければ「なし」。決められないものは、渡す前に利用者に聞く |

## 本質さの基準

十分でも、依頼された変更が本当の必要とずれていれば意味がない。次の危険信号があるときだけ、`references/naze-naze.md` のなぜなぜ分析で根本原因まで掘る。

- 依頼された変更と、それで解決したい問題が別の層にある（画面が遅い → 画面を直したい、だが原因は API やデータ）
- 同じ場所への修正が git の履歴に繰り返し出ている
- 「一旦」「とりあえず」が付いている
- 最近のマージの直後に出た問題
- 「遅い」「多い」に数字が無い

危険信号が無ければ、依頼どおりに受け取ってよい。迷ったら `bigdaddy:jev-gates` で「依頼された変更は根本原因と違う所に効いているか」を聞き、高ければ掘る。Jev が無効（exit 3）なら自分で同じ問いに答える。それでも迷えば掘る側に倒す。
利用者が「原因はわかってる」「そのままやって」と言ったら掘らない。

## 埋め方

空欄は次の順で埋める。前の手段で埋まるなら次に進まない。

1. **観察する。** コード・画面・ログ・データ・git 履歴を見る。観察で答えが出る問いは人に聞かない。仕組みを読むなら pstack の `how`、経緯なら `why`（SKILL.md を Read ツールで読む）。
2. **代理で答える。** 利用者の手元の `~/.claude/bigdaddy/proxy-answers.md` があれば先に読み、無ければ `references/proxy-answers.md` を読む。同じ状況の行が両方にあるときは手元のファイルを優先する。当てはまる行があれば、聞かずに決めて指示書の「代理で決めたこと」に書く。
3. **聞く。** 好み・仕様など、観察でも代理でも埋まらないものだけ。1 回に 1〜3 問、推奨を付けて `AskUserQuestion` で聞く。`AskUserQuestion` が使えない環境では、同じ形で本文に書いて止まる。外部送信と新しい feature flag はここで聞いて「仕様で決めたこと」に書く。実装セッションに聞かせない。

単純な依頼なら、観察だけで全部埋まり、質問ゼロで渡せるのが普通。
画面が変わる依頼の見た目と操作は、文章で聞かず、画面設計で見せて決める（次の節）。

## 画面設計

画面が変わる依頼では、指示書を渡す前に、決めた仕様を反映した画面設計を作り、利用者に見せて合意を取る。画面の食い違いを最後の QA まで持ち越さず、実装中の見た目の質問と手戻りを減らすため。画面設計は仕様の一部で、実装ではない。このセッションが作ってよい。

- **対象。** 新しい画面と、既存画面の構成・操作・状態が変わる依頼は全部。除くのは、要素の数・配置・操作の流れ・状態が変わらず、文言・色・余白などの値の差し替えだけで済む変更。除いたときは、指示書の「画面設計」に n/a と理由を書く。
- **道具。** 作業リポジトリの CLAUDE.md・AGENTS.md・DESIGN.md や project の skill が、画面設計の道具や手順（Figma のファイルなど）を指定していれば、それを最優先で使う。指定が無ければ Claude Design（`Artifact` の Design 型。作り方は `action: "quickstart"`、`intent: "design"`）を使う。指定の道具が使えない（認証切れなど）ときは、黙って飛ばさず、利用者に再認証を頼むか、Claude Design で代える。
- **デザインシステム。** 作業リポジトリの DESIGN.md・デザイントークンがあればそれに揃える。無ければ、組織の既定のデザインシステムを使う。
- **作り方。** 「今 → 望む状態」と「仕様で決めたこと」を反映する。成功条件に出てくる状態（空・エラー・読み込み中など）も 1 つずつ描く。画面に出す文言も画面設計に書き、実装役はそれを正本にする。決めた仕様に無い要素は足さない。
- **見せる。** URL を利用者に見せて、レビューしてもらう。指摘が出たら画面設計を直して、同じ URL で見せ直す（URL は変えない。合意の記録に、合意した日付を書く）。利用者の合意の返答を得るまで、指示書は渡さない。「お願い」「いいよ」も合意として扱う。
- **記録。** 合意は、利用者の返答の要約と日付を、指示書の「仕様で決めたこと」に書く（「代理で決めたこと」には書かない）。URL は、指示書の「画面設計」節に 1 つ書く。
- **topic の流れ。** 指示書が 2 枚以上のときは、全部の指示書を渡す前に、全部の画面を 1 つの画面設計にまとめて、レビューを 1 回で済ませる。URL は、各指示書の「画面設計」と、最終 PR の状態の JSON の `design` に書く。
- **あとから足す指示書。** QA の blocking や利用者の指示で足す指示書が、画面の構成・操作・状態を変えるときは、同じ URL の画面設計を直して利用者に見せ直し、合意を取ってから渡す（記録の日付を更新する）。再 QA は、直した画面設計に当たる全部の画面を照合し直す。画面の構成・操作・状態が変わらない修正は、いまの画面設計のままでよい。
- **実装中は画面設計を変えない。** 実装中は、合意済みの画面設計を変えない。画面の構成・操作・状態を変える差は、「親に返すもの」の（b）でも（c）でも、実行中の行には入れない。親が決めて、子 PR の「判断の記録」に親の決定として書き、最終 PR の確認で利用者が見る。直す必要があれば、利用者の指示として足す指示書（「あとから足す指示書」）で画面設計を直し、合意を取り直す。未着手の行は、渡す前なので、画面設計を直して合意を取り直してから渡してよい。構成・操作・状態が変わらない細部は、親が決めて終わりにする。
- **実装中。** 見た目・文言・操作は、画面設計を正本にする。画面設計が決めていない細部は、DESIGN.md・デザイントークン・周りの画面に揃える。見た目について利用者には聞かない。画面設計どおりに作れないときは、実装役が決めず、「親に返すもの」の（c）として親に返す（親の扱いは上の「実装中は画面設計を変えない」）。親が決めた差は、親の決定として PR 本文の「判断の記録」に書く。画面設計との差は、「本人に必ず返すもの」の方針の転換に当たらない。
- **QA。** QA は、画面設計と実装の画面を並べて照合する（`references/brief-template.md` の「QA subagent への依頼の型」）。QA には判断の記録を渡さないので、QA が画面の blocking にした差のうち、構成・操作・状態を変えない差で、親が承認して子 PR の「判断の記録」に親の決定として書いてあるものだけ、親が advisory に下げて最終 PR に載せる。画面設計の照合で確かめられなかった画面は、最終 PR の「人間が確かめること」に載せる。
- **画面設計を作れないとき。** Artifact も指定の道具も使えない環境では、黙って飛ばさず、画面設計を作れないことと理由を利用者に伝え、利用者が、画面設計を作れる環境の briefing で作ってから進める（除外には使わない）。

## 分ける

指示書は 1 枚 = 1 セッション = 1 PR。

- 原因や変更が独立して複数あれば、指示書を分ける。分けるか束ねるかは `bigdaddy:jev-gates` で決める（Jev が無効なら、依存と触るファイルを見て自分で決める）。
- なぜなぜ分析をしたときは、応急処置と恒久対策を別の指示書にする。依頼された変更を断るのではなく、両方並べる。
- 依存の順序を付ける。各指示書に、前提の指示書を書く。同じファイルを触る指示書どうしも依存として扱い、直列にする。依存の無いものは最初から並行に回す。
- project の CLAUDE.md がバックログ（Notion など）への登録を求める場合は、指示書ごとにバックログの行を作る。PR に貼る URL がここで決まる。バックログのツールが見えなければ `ToolSearch` で探す。認証切れなら黙って飛ばさず、利用者に再認証を頼む。

### 1 枚か、2 枚以上か

- 1 枚: default branch（例: main）向けの PR 1 本。マージは利用者がする。
- 2 枚以上: topic branch に子 PR を集め、最後に topic から default branch への PR 1 本（最終 PR）を利用者が確かめてマージする。親は、指示書ごとの状態を、最終 PR（draft）の本文の JSON に持つ。
  1. 親（このセッション）が、画面設計の合意（「画面設計」節）を取ったあと（合意した URL は、状態の JSON の `design` に書く）、親の worktree で default branch から `topic/<slug>` を切る。slug は依頼を表す短い英小文字にする。差分が 0 だと PR を作れないので、空のコミットを 1 つ足す。そのあと `git push -u origin topic/<slug>` を単独のコマンドで実行し（`git switch` などとつなぐと hook が止める）、topic から default branch への PR を draft で作る。各指示書に ID（例: `<slug>-01`）を付ける。draft PR の本文に、状態の JSON（手順 2）と、指示書の全文（指示書ごとに `<details>` で折りたたむ）を書く。各指示書の「repo の約束」には、PR の base（topic）と ID を書く。子のブランチ名、子 PR のタイトル、セッションの title には、必ずその ID を入れる（ブランチは `start_session` の `branch_name` を `<ID>/<要約>` にする。title と PR のタイトルは `<ID>: <要約>`）。
  2. 状態は、会話の外に置く。正本は、最終 PR の本文の `## 指示書の状態` 節にある JSON のコードブロック 1 つ。人が読む要約を JSON から書いてよいが、正本は JSON で、親が書き換えるのもこのブロックだけ（本文を `gh pr view --json body -q .body` で読み、このブロックだけを置き換えて、`gh pr edit --body-file` で渡す）。親だけが書き換え、子は触らない。形は次のとおり。

     ```json
     {
       "topic": "topic/<slug>",
       "design": null,
       "briefs": [
         {"id": "<slug>-01", "depends": [], "state": "未着手", "session": null, "pr": null, "qa": "未", "card": null, "started_at": null, "reason": null}
       ],
       "qa": "未実施",
       "reason": null
     }
     ```

     `design` は、利用者が合意した画面設計の URL（画面が変わる依頼でなければ null）。親だけが書き、QA に渡す。
     `state` は 未着手／実行中／PR あり／マージ済み／要確認 の 5 つだけ。`session` は `start_session` が返した id（起動の前は `"starting"`）、`pr` は子 PR の番号、`card` は offer や提案カードの task_id、`started_at` は `start_session` を呼んだ時刻。行の `qa` は 未／済、全体の `qa` は 未実施／実施中／済／要確認。`reason` は、「要確認」のときに理由を短く書く欄（それ以外は null）。遷移は次の表のとおり。

     | 状態 | 次の状態 | 遷移を起こす出来事（親が確かめて書き換える） |
     |---|---|---|
     | 未着手 | 実行中 | 親が `start_session` を呼ぶ前に、状態を実行中、`session` を `"starting"` にして書く。起動できたら id に書き換える。`offer` や提案カードで利用者が始める行も、カードを出す前に `"starting"` にする |
     | 実行中（`"starting"`） | 未着手 | 照合で、起動の実状態（ブランチ、PR、動いているセッション）が無いと確かめた。`session` を null に戻す。`card` があれば、先に `dismiss_task` で片付ける。`start_session` が失敗したときも同じ |
     | 実行中 | PR あり | base が topic の子 PR を見つけた。`pr` に番号を書く |
     | 実行中、PR あり | マージ済み | `gh pr view` で、子 PR が topic にマージされたと確かめた |
     | マージ済み以外のどの行も、全体の `qa` も | 要確認 | 親が、手順 4 の例外を見つけた。`reason` に理由を書き、利用者に返す |
     | 要確認 | 利用者の指示どおり | 利用者の指示を受け、親がその指示どおりに行を書き換え、「要確認」を外す。指示の中身ごとの遷移は決めない |
     | マージ済み | なし | 終わりの状態 |

  3. 表は、最後に観測した値として扱う。親は起きるたびに、判定の前に必ず実状態と表を照合し、食い違えば、実状態を正として JSON を書き直してから判定する。実状態は、ID と一致する origin のブランチ（ID の直後が `/`・`:`・終端のもの）、`gh pr list --base topic/<slug> --state all --json number,title,state,mergedAt,updatedAt,isDraft` の子 PR と、最終 PR の `isDraft`、`list_sessions`（`linked` なしで引き、title が `<ID>: ` で始まるもの）、`git log` の topic。たとえば、`session` が `"starting"` の行は、ID のブランチ、PR、動いているセッションのどれかがあれば、その実状態に直し、どれも無ければ未着手に戻す。全体の `qa` が実施中なら、QA の subagent が動いているか確かめ、動いていなければ未実施に戻す。子を始める前にも、その ID のブランチ・open の PR・動いているセッションが無いか確かめ、あれば新しく始めない。照合では、「要確認」の行の `state` は書き換えず、`session` と `pr` だけを更新する（「要確認」を外すのは、利用者の指示を受けたときだけ）。照合のあとで、手順 4 に当たるものを調べ、当たれば「要確認」にしてから、表だけから判定する。
  4. 次のどれかを見つけたら、親は、該当の行（QA の blocking は全体の `qa`）を「要確認」にし、`reason` を書いて、利用者に返す。返す文面には、親への指示（例: 続けて）が要ることも書く。自動では直さない。
     - 止まった子。子 PR（無ければ子のブランチ、どちらも無ければ `started_at`）の最終更新から 3 時間以上たち、`list_sessions` でそのセッションが動いていないと確かめたとき。または、子が終了を報告したのに、子 PR が topic にマージされていないとき（PR 無しで失敗を報告したときを含む）。
     - QA の blocking。
     - default branch の取り込みや子のマージで出たコンフリクトが、解消の子（手順 6）では収まらないとき。
     - 表と実状態の食い違いを、実状態から一意に直せないとき（マージ済みの行に関わるときは、全体の `qa` を「要確認」にする）。
     - 上の 4 つに当たらなくても、親が照合の結果から次の動作を 1 つに決められないとき。その行（行が決まらなければ全体）を「要確認」にする。判定が黙って止まる経路を残さないための条件。
  5. 親は、子の終了通知（`list_sessions` の `linked: true` と、子の完了の note）で起きる。起きたら手順 3 の照合をし、そのあと表だけから、次の 1 つを選ぶ。親を閉じたあとの再開も、同じ判定から入る。
     - 「要確認」の行か、全体の `qa` が「要確認」なら、待つ（利用者の返答待ち）。新しい子は始めず、QA も回さない。予約は要らない。利用者の指示を受けたら、親がその指示どおりに行を書き換え、「要確認」を外して、手順 3 からやり直す（指示の例: 置き換える、打ち切る、成功条件を書き換えて直す指示書を足す。止まった子には「続けて」だけでは足りない）。
     - 状態が未着手で、依存がすべて「マージ済み」の行があれば、追従（default branch が進んでいたときだけ）と取り込みをしてから、始められる行をすべて始める（手順 6）。
     - 全部の行が「マージ済み」で、全体の `qa` が未実施、または、行の `qa` が未の行があるなら、追従（毎回必ず）をしてから、QA を回す（手順 8）。追従でコンフリクトが出たら、解消の行を足して手順 6 で始め、QA は回さない。全体の `qa` が実施中なら、待つ。
     - 全部の行が「マージ済み」で、行の `qa` がすべて済、全体の `qa` が済で、最終 PR の `isDraft` が false なら、利用者のマージ待ちと伝えて、終わる。`isDraft` が true なら、`gh pr ready` を実行してから伝える。
     - どれでもなければ、待つ。待つときは、待っている行と、再確認する時刻（動いている子のうち最も早い最終更新から 3 時間後。ただし今から 1 時間後より前にはしない）を利用者に伝える。動いている子（実行中、PR ありの行）が 1 つも無いのに待つことになったら、時刻が決まらないので、全体の `qa` を「要確認」にして `reason` を書き、利用者に返す。`ScheduleWakeup` や Monitor が使えるなら、その時刻の再確認を予約する。再開した親は、前の親が始めた子と linked でないので、終了通知が届かない。利用者の依頼のたびに、手順 3 からやり直す。
  6. 子を始める手順。始める前に、origin の topic をローカルの topic に取り込む（`start_session` の `source_branch` はローカルのブランチを取る）。親は topic を checkout したままにしない。push したら元のブランチに戻り、取り込みは `git fetch origin topic/<slug>:topic/<slug>` で行う。子の PR の base は topic で、タイトルは `<ID>: <要約>` にする。子を始める `start_session` の `title` も `<ID>: <要約>`、`branch_name` は `<ID>/<要約>` にする。
     topic を default branch に追従させるのは親の仕事で、rebase と force-push はしない。時機は 2 つ。新しい子を始める前（default branch が進んでいたときだけ）と、QA の直前（毎回必ず）。
     - 親は `git fetch origin` で origin の topic と default branch を取り込む。一時 worktree を `git worktree add --detach <path> origin/topic/<slug>` で作り、`git merge origin/<default branch>` を実行する。
     - きれいに merge できたら、`git push origin HEAD:topic/<slug>` を別のコマンドで実行し（merge と push をつなぐと hook が止める）、一時 worktree を消す。push が non-fast-forward で弾かれたら、worktree を消して作り直し、`git fetch origin` からやり直す。
     - コンフリクトが出たら、親は自分で解かない。途中で止まった一時 worktree で `git merge --abort` を実行し、worktree を消す。そのうえで、解消の指示書を新しい行として JSON に足し（状態は未着手）、待たせる行（子を始める前の追従なら、始めようとした子）の `depends` にも、解消の行の ID を足す。JSON にマージ前の解消の行があるうちは、追従をしない（取り込みだけで子を始める）。解消の子でも収まらないときは、手順 4 のとおり「要確認」にする。
     - 解消の子は、default branch を取り込んでコンフリクトを解き、隔離レビューを通してから、merge コミットで topic にマージする。CI が緑なら、`gh pr merge <番号> --merge --match-head-commit <SHA>` を単独のコマンドで実行する（squash だと default branch のコミットが topic の祖先にならず、追従が同じコンフリクトで止まり続ける）。リポジトリが merge コミットを許さないときは、手順 4 のとおり「要確認」にする。隔離レビューで見るのは、解消した箇所と、取り込んだ変更との組み合わせ。
  7. 子は、隔離レビューで blocking が 0 件になった head を `review-stamp.sh` で記録する。CI が緑なら、子が自分で topic へマージして worktree を消す。子はそこで終わり、QA は始めない。手順は `references/brief-template.md` の「PR とマージ」。
  8. 親は、opus medium の新しい subagent に QA を回す。回す前に、全体の `qa` を実施中にする。QA の手順のうち、成功条件の確かめ方（画面・API・CLI・データなど）は、作業リポジトリの CLAUDE.md・AGENTS.md や project の skill（`.claude/skills/` など）が指定していれば、それを最優先で使う。差分全体のレビューと、成功条件の分類は、指定があっても行う。指定が無いと決める前に、ToolSearch や skill の一覧で探す。指定が無ければ、画面は標準として、subagent がブラウザ（built-in browser など）と iOS シミュレータでの確認を自分で行う。画面以外（API・CLI・データなど）は、各指示書の「成功条件と確かめ方」に従って実行し、出力を証拠にする。QA の結果には、手順の出どころ（リポジトリの指定か標準か）と、確認を行った者（subagent か親か）を書く。subagent がそれらのツールを使えないときは、親が自分で確認する。依頼の型は `references/brief-template.md` の「QA subagent への依頼の型」。渡すのは、各指示書の「受入条件・不変条件」と「成功条件と確かめ方」の原文と、topic と default branch の差分と、状態の JSON の `design`（画面設計の URL。null なら渡さない）で、実装役の判断理由は渡さない。画面設計がある QA は、画面設計と実装の画面を並べて照合する。subagent は topic の checkout の上で確かめるので、親が `git worktree add <path> origin/topic/<slug>` で用意して、そのパスを渡す。
  9. 親は、subagent の結果と、子 PR 本文の「判断の記録」を集めたものを最終 PR の本文に書く。本文は `gh pr edit --body-file` で渡す。QA で「確かめられなかった」成功条件だけを、本文の「人間が確かめること」にチェックリストで載せる。URL・ログイン状態・端末などの条件も書く。載せるのは、物理端末でしか確かめられないもの、本番の外部サービスや本番データが要るものなどの例外に限る。QA の結果を受け取ったら、blocking が 0 件のときは、対象の行の `qa` と全体の `qa` を済にして、ready にする。blocking があるときは、結果を本文に書き、全体の `qa` を「要確認」にして `reason` に blocking の要約を書き、ready にせず、利用者に返す（手順 4）。利用者の指示（直す指示書を足す、成功条件を書き換える、など）を受けたら、親がその指示どおりに書き換える（行を消すときは、その ID を他の行の `depends` からも消す）。直す指示書を足したときは、その行がマージされたあと、QA はその行の差分と落ちた条件だけやり直す（画面の構成・操作・状態を変える修正は、先に「画面設計」節のとおり合意を取り直し、再 QA で当たる全部の画面を照合し直す。直した画面設計とマージ済みの実装との差も、足す指示書が受け持つ。画面設計を開けず確かめられなかった画面は、例外として「人間が確かめること」に載せる）。その再 QA で blocking が 0 件なら、全部の行の `qa` と全体の `qa` を済にして、ready にする。利用者の確認で落ちた条件も、利用者の指示として同じに扱う。親はマージしない。
 10. 利用者が最終 PR を確かめてマージする。マージのあとの topic の削除も利用者が決める。
  - 親を閉じたときは、最終 PR の JSON が状態を持つ。利用者が新しいセッションで briefing に「topic/<slug> の QA」と頼めば、その PR の JSON を読み、手順 3 の照合と手順 5 の判定から、同じ流れで続ける。
- 守るのは文章ではなく hook。`hooks/topic-merge-guard.sh` は、default branch に変更を入れる agent のツール呼び出しを止める。
  - default branch に向く `git push`（記録があっても止める）と `git subtree push`
  - base が default branch の `gh pr merge`（`--auto` 付きも含む）
  - `gh api` の `/merge`・`mergePullRequest`・`enablePullRequestAutoMerge`、`git/refs`・`contents`・`updateRef` などへの直接の書き込み
  - マージする MCP ツールと、ブランチに直接書く MCP ツール（書き込み先が default branch か、読めないとき）

  base が topic の `gh pr merge` は、次の 3 つがすべて成り立つときだけ通す。PR の head が `review-stamp.sh` の記録と一致する。`--match-head-commit` でその SHA を固定している。cd 以外のコマンドとつないでいない。`--disable-auto` だけの呼び出しは通す。hook は default branch をリポジトリから求め、求められないときと PR を特定できないときは止める。
  止められないのは、スクリプトファイル経由・alias・変数展開などの間接実行と、`gh repo edit` のような上に無い書き込み。守る相手は agent の勘違いと先走りで、意図的に回避する agent は想定しない。利用者が GitHub の画面や自分のシェルでマージするのは本来の経路なので、対象外。

## 決めたら点検する

プレイブックの選択、掘るか掘らないか、分けるか束ねるか、見立ては、決めたら `bigdaddy:logic-audit` の決定モードで点検する。指示書の「設計」が、「なぜ」に本質的に沿っているか（やろうとしていることが目的に合っているか）も、hook の求めとは別に、子に渡す前に必ずここで点検し、結果を「代理で決めたこと」か「仕様で決めたこと」に書く。重要と判定されたものは、指示書の「代理で決めたこと」に結論・前提・退けた代案・覆る条件を書く。jev-gates のスクリプトを実行すると hook が点検を求めるので、そのときに行う。

## 合意と受け渡し

次のどれかに当たるときは、渡す前に利用者に見せて合意を取る。

- 見立てが依頼と違う（依頼された変更とは別の手当てを提案する）
- 代理で決めたことに、外れると手戻りが大きいものがある
- 画面が変わる依頼（除外は「画面設計」節の基準に当たる変更だけ）で、画面設計に利用者の合意が無い。見せる形は画面設計の URL で、他の項目と同じ 1 回の確認にまとめる

見せる形:

```text
依頼: <利用者が言ったこと>
見立て: <本当の必要・根本原因>（根拠: <証拠>）
提案: <指示書の要約>（応急処置 / 恒久対策）
画面設計: <URL>（画面が変わる依頼のときだけ。見てほしい点を添える）
```

見立てが依頼と違うときは、見せる前に `bigdaddy:logic-audit` の決定モードで見立てを点検する。根拠が支える強さで書き（「〜だ」と「〜の可能性が高い」を区別する）、未確認の前提は前提として示す。

どれにも当たらなければ合意を省いて渡す。
渡すときは `references/brief-template.md` の指示書を `spawn_task`（このアプリでは `start_session`）のプロンプトにする。どちらも使えない環境（Cursor など）では、指示書を返信の本文に出し、利用者が新しいチャットに貼れるようにする。
指示書を書くこのセッションは計画役なので opus medium で動かす。実装セッションの主は、指示書の推奨モデル（`route-model.sh --session <playbook>`）で動かす。Feature・Refactoring は設計が指示書で決まっているので sonnet high、原因が未確定の Bug fix・Perf issue などは opus medium。

0. 指示書が 2 枚以上のときは、先に topic を切って push し、draft の最終 PR を作り、各子の `start_session` で新しい worktree の元のブランチに topic を指定する（`source_branch`）。指定できない環境では、子の指示書の「repo の約束」に、topic を元に worktree を作ると書く。
1. `start_session` を `context: "fresh"` で呼ぶときは、`model` に推奨モデルの id、`effort` に推奨の effort を渡す。id は family 名ではなく、モデルの選択メニューの id（例: sonnet なら `claude-sonnet-5-5`）。この引数は親と同じか安いモデルだけ受け付け、高いモデルは無視される。
2. 引数で渡せなかったとき（`offer` カードや提案カードから利用者が始めた場合など）は、開いたあとに切り替える。この経路でも、カードの `title` には、`<ID>: <要約>` を付ける。開いたあとの子は、親が「分ける」節の手順 3 の照合で見つけ、JSON の `session` に id を書く。カードの task_id は、カードを出して返ったらすぐ `card` に書く。`list_sessions` を `linked: true` で呼んで子セッションの `sessionId` を取り、`model` が推奨と違えば `set_session_model` に推奨モデルの id を、`set_session_effort` に推奨の effort を渡す。切り替わるのは次のターンからなので、最初のターンは開いたときのモデルで動く。セッションは自分のモデルを変えられない（`set_session_model` は自分自身を対象にすると断られる）。
3. 子セッションが見つからない、または切り替えが断られたときは、利用者に「実装セッションのモデルを <id>、effort を <effort> に、モデルの選択メニューで変えてほしい」と伝える。`spawn_task` が無い環境（クラウドセッション、CLI など）では、指示書を本文に出す。利用者が同じセッションでの実装を認めたら pstack の `poteto-mode` と指示書の「使う原則」の SKILL.md を Read ツールで読んで切り替え、認めなければ新しいセッションに貼れる形で渡して止まる。依存のあるものは、前の指示書の子 PR が topic にマージされてから渡す。指示書が 1 枚なら、渡したあとは、子の PR が出るまで、子からの `SendMessage`（「親に返すもの」）に応じる。2 枚以上なら、全部の子が topic に入り、親が QA を回して最終 PR を ready にするまで、親は待つ。

## 本人に必ず返すもの

実装セッションが利用者に返す項目はここだけ。親に返す項目は、次の「親に返すもの」にある。指示書の「本人に返すもの」と「親に返すもの」には、それぞれの節をそのまま貼る。ここに無いものは、実装中に利用者に聞かない。前段（briefing）が渡す前に聞くものは、「埋め方」と「合意と受け渡し」に書いてある。

返す:

- default branch（例: main）への PR のマージ。agent は default branch に入れない。topic branch への子 PR は、隔離レビュー済みの head なら子セッションがマージする。
- 本番データへの書き込み
- 指示書の「仕様で決めたこと」に書かれていない外部への送信（Slack、顧客、外部サービス）と、新しい feature flag の追加。書かれた範囲なら聞かずに実行する。
- 方針の転換。指示書の「今 → 望む状態」または「成功条件」を書き換えないと完了できないときだけ。

返さない:

- 上に当たらず、「親に返すもの」にも当たらない局所的な設計の選択（関数名、内部の型の切り方など）。自分で決め、PR 本文の「判断の記録」に結論・前提・退けた代案・覆る条件を残す。topic の場合、記録は最終 PR に集まり、利用者が後から見る。

上の 4 項目のどれに当たるか迷うときは、あとから取り消せるかで分ける。取り消せるなら、次の「親に返すもの」に当たらない限り、決めて記録する。取り消せないなら、設計の選択は親に、それ以外は利用者に返す。

## 親に返すもの

設計や全体の方針を決める意思決定は、親（briefing のセッション）が渡す前に済ませる。子に渡す時点で、指示書の「設計」は「あとは淡々と実装をやるだけ」の状態になっている（「十分さの基準」の「設計」。opus medium に渡すものを除く）。指示書に無い設計の選択が出たときは、次の（a）〜（c）のどれかに当たるものを、実装役が決めずに親に返す。（d）は設計の選択ではないが、同じ経路で親に返す。

- （a）「今 → 望む状態」に至る手段を変えるもの
- （b）他の指示書や全体の方針に影響するもの
- （c）画面設計との差
- （d）2 回目以降の隔離レビューで出た blocking。設計の選択ではないが、実装役は直さず、指摘の全文を親に送る（下の「blocking の仕分け」）

当たらない局所的な設計の選択は、「本人に必ず返すもの」の「返さない」のとおり、実装役が決めて記録する。1 回目の隔離レビューの指摘のうち設計の変更が要るものも、（a）〜（c）に当たれば親に返す。

返し方:

- 親には `SendMessage` で送る（deferred tool なので、先に `ToolSearch` で `select:SendMessage` を読み込む）。`to` は、指示書の「親に返すもの」に書かれた親セッションの id（`local_…`）。親は自分の id を `mcp__ccd_session_mgmt__get_session` の `session_id: "self"` の `sessionId` で得て、指示書に書く。子は、指示書の id に加えて、自分の `get_session("self")` の `parentSessionId` からも親を求められる。どちらも得られない環境（Cursor など）では、親に返す経路が無いので、利用者に返す。
- 送るときは、その部分の作業を止め、影響しない部分は進める。送る文面は、何を決めたいか、候補と推奨、止めた部分と進めた部分を、最初の 1 行で分かるように書く。
- 親は、受け取ったら、決めて（重要なものは「決めたら点検する」のとおり点検して）、同じ送信元に `SendMessage` で返す。他の指示書に影響する決定は、親が該当する指示書も直す。未着手の行は、指示書本文と、topic なら最終 PR 本文の `<details>` の全文を直し、実行中の行は `SendMessage` で伝える。決定が画面の構成・操作・状態を変えるときの扱いは、「画面設計」節の「実装中は画面設計を変えない」に従う（実行中の子には、現行の画面設計のまま進めるよう伝える）。親は、子の「判断の記録」の親の決定を、自分が送った決定と照合してから、QA の blocking を advisory に下げる。照合できないとき（親を閉じて再開したなど）は、下げずに全体の `qa` を「要確認」にする。再開した親は、実行中の子に、新しい親の id を `SendMessage` で伝える。子は、親の決定を PR 本文の「判断の記録」に「親の決定」として書く。
- 親が応答できないとき（`get_session` で親が `isArchived` になっている、または、影響しない部分を終えても返信が来ない）は、止めた部分を未決として PR 本文に書き、利用者に返す。topic の子は、止めた部分が残るあいだは topic にマージせず、完了を報告して止まる（親は手順 4 の「止まった子」として扱い、行を「要確認」にする）。これが、設計と見た目の選択が利用者に届く唯一の経路になる。

### blocking の仕分け

隔離レビューの 1 回目は全体を見る。2 回目以降は直した差分だけを対象にし、受入条件・不変条件を破る blocking だけを返させる。advisory は返させない。除外は、親が全体の再レビューを指示したときだけ。範囲と指示は `bigdaddy:review-triage-loop` の `references/isolated-review.md`。

- 2 回目以降で blocking が出たら、実装役は直さずに指摘の全文を親に送る。前回送った指摘と同じ周辺かも 1 行で書く。
- 親は指摘ごとに「目的に本質的で直す」「直さない（理由）」「別 PR」に仕分けて、同じ送信元に返す。「直す」と返したものだけを実装役が直し、その差分を次の回のレビューにかける。必要と判断したときだけ、全体の再レビューを指示する。「直さない」「別 PR」と返して判断の記録に書いた blocking は、記録に進むときの blocking の数に入れない。
- 2 回目以降で、同じ周辺（同じファイルの同じ節・関数、または同じ不変条件の項目）に blocking が 2 回続けて出たら、親はその部分を PR から外して別 PR にするかを判断する。外すなら、実装役がその部分の差分を戻し、follow-up として PR 本文に書く。成功条件を書き換えないと完了できなくなるときは、方針の転換なので、親が利用者に返す。
- 仕分けの結果と外す判断は、親が実装役に返し、実装役が PR 本文の「判断の記録」に親の決定として書く。直さない理由と、別 PR にしたものの扱いも書く。
- 親が応答できないときは、上の「返し方」の最後の項目のとおり、止めた部分を未決として PR 本文に書き、利用者に返す。

## 文章

日本語の文章は yomiyasu（`yomiyasu:yomiyasu`）の基準で書く。書く物の重さで使い方を変える。

| 書く物 | 使い方 |
|---|---|
| 会話の返答 | yomiyasu の本文は読まず、`references/writing.md` の要点だけ守る。本文は約 66KB あり、毎ターン読むと会話が太る |
| ドキュメント、PR の概要、Issue、コミット本文、Notion のページ | pstack の `technical-writing` と `unslop`（SKILL.md を Read ツールで読む。Skill ツールでは起動できない）で下書きを書き（構成と文の規律）、最後に yomiyasu で日本語として推敲してから出す。長い文書や会話が長いときは、推敲を subagent に渡し、仕上がった本文だけを受け取る |
| 英語の文章 | pstack の `technical-writing` と `unslop`（SKILL.md を Read ツールで読む） |

順番は `technical-writing` → `unslop` → yomiyasu に固定する。食い違ったときは、日本語の表現については yomiyasu を優先する。yomiyasu は今までどおり Skill ツールで起動する。yomiyasu と他の日本語推敲の skill（`japanese-tech-writing` など）は重ねない。
