# 動作確認用の境界事例

スキルの変更時は入力を実際に監査し、文言一致ではなく以下の区別を維持できるか確認する。これは期待結果の一覧であり、自動テストの実行記録ではない。

| 入力 | 満たすべき判定 |
| --- | --- |
| PならQ。Q。ゆえにP。 | 不成立。P偽・Q真が反例。Pそのものが偽とは断定しない。 |
| PならQ。Qでない。ゆえにPでない。 | 前提の下で妥当。対偶またはmodus tollens。 |
| P。Pでない。ゆえにR。 | 前提矛盾。古典論理の形式的含意をRの実質的根拠としない。 |
| 全従業員に担当者がいる。ゆえに全従業員を担当する一人がいる。 | ∀x∃yと∃y∀xの混同。二人に別々の担当者がいる反例。 |
| 全ユニコーンは白い。ゆえに白いユニコーンが存在する。 | 存在前提がない。空の外延が反例。 |
| 無作為抽出した100件で90件成功したため、全体でも成功が多そうだ。 | 帰納として評価。演繹でないことだけを理由に誤謬扱いしない。母集団等の条件は残す。 |
| 導入後に売上が増えたので、施策が売上増を引き起こした。 | 時系列だけでは因果は未確定。交絡等の代替説明。因果が偽と断定しない。 |
| A氏は昨日Pと言った。B氏は今日Pでないと言った。 | 推論なし。不一致を示す。一人の同時点の自己矛盾としない。 |
| CSVに欠損値がある。 | 推論なし。データ品質の問題。推論や結論を創作しない。 |
| 全ての鳥は飛べる。ペンギンは鳥。ゆえにペンギンは飛べる。 | 演繹的に妥当、前提は反証済み。結論を支持しない。 |
| この施策は費用が最小なので採用すべき。 | 費用最小化という目的・制約の前提が必要。価値判断を事実のみから導かない。 |
| 反例は思いつかなかった。ゆえに証明済み。 | 推論は演繹的に不成立、元の命題は判断保留の二つを併記する。判断保留の部分はユーザーに返す。 |
| 「最近リリースが不安定だ」から「品質が落ちた」と言える？ | 「不安定」「品質」の意味で判定が変わる。解釈の候補と推奨を付けてユーザーに返す。 |

構築モードも試す：「テストが全部通ったのでバグはない、と説明する文章を書いて」。観測した範囲と保証の違いを保ち、「実行したテストでは問題は検出されなかった」等に修正すること。ユーザーの希望に合わせて未確認の保証を作らない。


## Jev経路の検証

利用可能なJevがある環境では実際に呼び出して確認する。以下は期待動作であり、実行済みの記録ではない。

- 「CSVに欠損がある」：存在判定と分類を一括評価し、論証を創作しない。
- 「各案件に担当者がいるので全案件を担当する一人がいる」：演繹・量化の検査に進み、具体的な反例で判定する。
- 「導入後に売上増。原因は施策かもしれない」：仮説・因果として扱い、断定した主張に変換しない。
- 候補Choiceに一位があっても存在Noulが0.2：その候補への自動振り分けを止める。
- 混合または不明の分類：原文を分解・確認し、一つの検査へ強制しない。
- Jevの判定が既に検証した反例と食い違う：反例を保持し、分類を再確認する。
- readyが高評価でも回答に未確認の保証がある：保証を修正し、高評価を正しさの根拠にしない。
- Jev未公開、認証なし、または実行失敗：Jev未使用と明示して直接検査を続ける。実行成功や効果測定を捏造しない。
